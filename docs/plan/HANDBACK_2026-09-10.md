
afterwards from `[build_info] running build <sha>` in the Render log —
`/health` returns a hardcoded 1.0.0 and always has.

**One residual to listen for, and it is a deliberate trade.** On a fresh day
the caller's already-heard clock times are pushed out of the readout, and
sometimes that includes the day's **earliest** slot. Corpus example: they heard
08:00 on Tuesday, so Wednesday now opens at 09:40 rather than 08:00. The 08:00
is still bookable and still reachable by asking — but if it sounds wrong on the
call, that is the shape to report, not a regression.

`caller_wants_soonest` already exempts anyone who asked for the earliest
(B-137/B-142), so this only affects callers who did not.

## 3. Four things found tonight that nobody was looking for

None is fixed. Each is one line or thereabouts, each is on a live path, and
each therefore has a call gate.

1. **Stage C's gate is blind to half of what it covers.**
   `_record_stood_down_slots` (`llm_stream.py:3717`) returns silently when it
   resolves nothing. It needs a failure line of its own.
2. **`presented_days` is never recorded in single-day mode.** Populated on all
   53 `multi_day` offers, empty on all 24 `single_day` ones — so B-95's
   presented-vs-bookable split is structurally invisible in exactly the mode a
   caller reaches by naming a day. One argument at the single-day call site.
3. **The tool-vs-plain latency split cannot be measured at all.** Nothing per
   turn records whether a tool ran. One field on `TurnTiming` fixes it, and
   without it the runbook's own T2 question has no answer.
4. **Historical, no action:** jv_v1 wrote `ttfa_ms`/`content_ttfa_ms` as an
   absolute clock reading rather than a delta — 1,934 turns, 22–23 Aug, seven
   retired build SHAs, values around 138 days. Unrepairable (`t0` was never
   stored) and no clinic has done it since. Now filtered by `IMPOSSIBLE_MS`,
   which prints what it dropped. Worth knowing because the **first** run of that
   analysis reported a p50 of 11,849,310 s and the table looked entirely normal.

## 4. The number that should change what gets worked on next

**p95 caller-perceived latency is 8.28 s against a published bar of 1.5 s, and
86.2 % of all turns are over that bar.** 18.7 % of turns have more than three
seconds of *total silence* — the second published bar, also breached.

`llm_ttft` (5.62 s at p95) and `chunk_gate` (3.58 s) are the whole of it.
`tts_first_byte` is 0.19 s and should come off the list. The deterministic
paths answer in **0.13 s** against 3.06 s for a generated turn.

No clinic is meaningfully faster than another, so this is engine work, not
configuration, and a fix helps all four equally. Ranked plan in
`LATENCY_DISTRIBUTION_2026-09-10.md` §8.
