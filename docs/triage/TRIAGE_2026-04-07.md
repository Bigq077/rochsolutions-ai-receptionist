## Ranked root causes

### 1. `PRESENT_TIMES` has no exit when the caller's turn isn't a time ordinal — severity 2

- **Hypothesis:** `app/media_streams/flow.py`, the `PRESENT_TIMES` state and its
  `slot_ordinal_selection` handler. The handler claims every utterance at that
  state and re-asks when it cannot parse an ordinal, with no escape and no
  escalation, so the call loops until the scenario runs out of responses.
- **Scenarios (23):** 2.6, 2.7, 4.1, 4.2, 4.3, 4.4, 4.5, 5.1, 5.2, 5.3, 8.1,
  8.2, 8.3, 8.4, 8.5, 11.3, 11.7, 11.14, 12.4, 13.3, 13.4, 14.1, 14.3
- **Stall point:** stuck 3–7 consecutive turns in `PRESENT_TIMES`,
  `handled_by=slot_ordinal_selection`, `selected_slot=None`, `flow_step=10`,
  `end=completed`.
- **Discriminating evidence** — of the calls that reached `PRESENT_TIMES`:

  | | reached | left the state |
  |---|---|---|
  | passing calls | 46 | 30 |
  | failing calls | 28 | **5** |

  Failing calls are not failing *at* slot selection by coincidence; they are
  failing *because they cannot leave it*.
- **Evidence (4.1, turn traces):**
  ```
  PRESENT_DAYS ->PRESENT_TIMES   by=slot_ordinal_selection  said='the first one please'
  PRESENT_TIMES->PRESENT_TIMES   by=slot_ordinal_selection  said="yes that's right"
  PRESENT_TIMES->PRESENT_TIMES   by=slot_ordinal_selection  said='john smith'
  PRESENT_TIMES->PRESENT_TIMES   by=slot_ordinal_selection  said='yes'
  ```
  > SUSIE: "I didn't quite catch that — could you say that again? On Tuesday 7th
  > April I've got nine o'clock in the morning or five o'clock in the afternoon
  > — which suits you?"

  The caller **was heard** every turn (`user_text_raw` is populated). This is a
  matching/advance defect, not an ASR or audio defect.
- **Ruled out:** a one-turn desync introduced earlier at `PRESENT_DAYS`. 29/29
  failing calls that reached `PRESENT_DAYS` consumed a turn there without
  advancing — but so did **42 of 46 passing calls**. The desync is normal and
  usually absorbed. It is not the cause; it is the load `PRESENT_TIMES` fails
  under.
- **Discriminator for `susie-debug`:** read the `PRESENT_TIMES` branch of
  `ask_current_question()` / the slot-ordinal matcher in `flow.py`. Question to
  answer: after N unmatched utterances at `PRESENT_TIMES`, what is supposed to
  happen? If the answer is "nothing", that is the bug.
- **Next action:** hand to `susie-debug` as scenario **4.1** (smallest
  reproduction: five responses, single clinic, clean audio).

### 2. Other states also consume a turn without advancing — severity 2

Same shape as cluster 1 at different states. Kept separate because the handler
differs, but they may share one root cause — see the cascade note.

- **Hypothesis:** `flow.py` state handlers claim the turn and re-ask instead of
  advancing or escalating. Note `COLLECT_NAME` is being handled by
  `slot_ordinal_selection` — **the slot handler is eating turns in a state it
  does not own**, which is a concrete, checkable defect.
- **Scenarios (7):**

  | Stall state | `handled_by` | Turns stuck | Scenarios |
  |---|---|---|---|
  | `COLLECT_NAME` | `slot_ordinal_selection` | 2 | 18.7, 19.4 |
  | `RETURNING_TREATMENT_PLAN` | `detect_intent` | 5 | 19.1, 19.3 |
  | `RETURNING_RECENCY` | `detect_intent` | 5 | 19.2 |
  | `COLLECT_REASON` | `detect_intent` | 3 | 18.8 |
  | `COLLECT_PHONE` | `collect_phone_no_digits` | 1 | 18.10 |

- **Evidence (19.4, "Name given with professional title"):**
  > SUSIE: "I didn't quite catch that — could you say that again? Who am I
  > booking in today?" ×2

  The caller gave a name with a title ("Dr."); it was not accepted, and the
  state had no other way out.
- **Discriminator:** does `slot_ordinal_selection` have a state guard? If it can
  run while `current_state == "COLLECT_NAME"`, cluster 2's first row is the same
  bug as cluster 1.
- **Next action:** `susie-debug` on **19.4** after cluster 1 is fixed — two of
  these five rows may disappear with it.

### 3. WebSocket session lost mid-call — severity 3

- **Hypothesis:** `app/media_streams/connection.py` WS lifecycle, or the test
  harness's direct-WS mode. `end_reason="direct_ws_session_lost"` means the call
  did not end, it was dropped.
- **Scenarios (2):** 16.6, 16.7
- **Stall point:** 16.6 dropped at `flow_step=2`; 16.7 dropped at `flow_step=9`
  after stalling 5 turns in `PRESENT_DAYS`.
- **Evidence:** these are the only two calls in 118 with this `end_reason`; both
  also fail `flow_completed`, which no other failure does.
- **Caveat:** 2 of 118 is thin. Do not build a theory on it — check whether it
  recurs in the next run before spending time.
- **Next action:** watch, don't chase. If it recurs, it outranks cluster 2 —
  a dropped call is a caller hearing silence.

### 4. Evaluator false positives on `no_state_corruption` — severity 5

- **Hypothesis:** not a Susie bug. `no_state_corruption` is a Claude judgement in
  `tests/auto/evaluator.py`; these two calls **completed their bookings**.
- **Scenarios (2):** 18.6, 18.9
- **Evidence (18.9):**
  > SUSIE: "Perfect — you're all booked in. We'll send a confirmation text
  > shortly. Have a great day!"

  Both show `flow_step=15` (`CONFIRM_BOOKING`), a selected slot, and no stall.
- **Next action:** none in the engine. If this recurs at the same rate, tighten
  the `no_state_corruption` field definition in the evaluator prompt — both calls
  contain a silence re-ask, which the judge appears to be reading as corruption.
